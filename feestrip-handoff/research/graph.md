# The Graph for FeeStrip — partner recommendation

Reviewed 2026-09-11. Source/architecture research only: no account created, provider key used, pipeline run, subgraph deployed, money spent, or live query success claimed.

**Recommend The Graph as partner three if FeeStrip includes a serious buyer pricing terminal.** Its useful role is underwriting a native-USDC fee claim: explain the asking price using the actual frozen range, historical market regimes, liquidity competition, and previous realized payouts. Keep the historical-state verifier and custody contract authoritative for payout and NFT release. Compared with the proposed Privy treasury-policy direction, Graph contributes more directly to the instrument's price discovery; Privy is a stronger choice if treasury operating controls become the primary product. This is a product-fit judgment, not a finding about Privy's prize eligibility.

## Prize fit

The $5,000 composable/standardized track accepts either two Graph products or meaningful use of an established standardized schema. It requires live provider data, public code and a 2–4 minute demo. A single ordinary subgraph is insufficient. Compose **Substreams + a FeeStrip Subgraph**; explicitly show their joined result. Two ordinary subgraphs are not two distinct products, and Hasura/ClickHouse are not extra Graph products. [Official prize](https://ethglobal.com/events/ethonline2026/prizes/the-graph)

There is no need to force FeeStrip into a vault standard or manufacture a new “standard” solely for eligibility. Messari's DEX AMM Extended schema does model concentrated liquidity, but the inspected Messari repository tree contained no Uniswap-v4 implementation. Uniswap's own v4 schema is bespoke. A genuine standardized comparison across existing DEX implementations is an alternative, but less directly useful than range-specific v4 analysis. [Graph standardized schemas](https://thegraph.com/docs/en/subgraphs/existing-subgraphs/standard-subgraphs/), [Messari repository](https://github.com/messari/subgraphs)

## Concrete integration

**Proposed architecture:** a reusable v4 Substreams module feeds a pool-history database; a Studio-hosted FeeStrip subgraph indexes the escrow/series lifecycle; the pricing service joins them on `(chainId, PoolManager, poolId)` and series block boundaries. Series entities retain PositionManager/tokenId, original owner, frozen ticks/liquidity, payout token, claim supply, baseline, cutoff block, capture/return status, finalized payout and redemption history. Index actual emitted trading events where reliable order/series attribution exists; ordinary ERC20 transfers alone do not establish trade prices.

The buyer sees a decision, not just charts:

1. **Break-even:** for a fraction `q/Q` of the whole-period claim bought for `P` USDC, gross total-series break-even is `P × Q/q`. Show how much additional USDC is needed beyond the clearly labeled indicative accrual. Include execution costs in a separate net-return calculation.
2. **Range risk:** time/block-weighted price-in-range history, sustained excursions beyond either boundary, and changes in competing active liquidity. Derive occupancy from ordered price changes and timestamps/blocks, not the fraction of swaps ending in range. A swap crossing a boundary is not wholly attributable to its ending tick.
3. **Modeled price range:** replay/stress scenarios for the remaining block window and a documented comparison against completed series' actual finalized payouts. Show sample size and out-of-sample errors; sparse series history remains sparse. Prices are maker judgments and models, not promises.
4. **Action:** the buyer uses this report to accept/reject an Aqua offer; a maker can choose a quote from the same report. Graph data never authorizes spending, settles a claim, returns principal, or replaces SwapVM/onchain validation.

A strong demo changes a range or selects a different series and visibly changes break-even context and modeled downside using fresh data. Show two comparable series whose similar pool-level volume produces different range exposure. The reusable module should expose pool history independently of FeeStrip, accept network/manager parameters, and have a documented downstream interface; the same extraction code should work under another supported network configuration.

**Do not compute “exact historical fees” as volume × fee × today's liquidity share.** Intra-swap crossings, historical active-liquidity changes, fee denomination and protocol fees defeat that shortcut. Aggregate fees in USD also mix the two fee currencies, whereas FeeStrip sells one native token's growth. The event pipeline supports risk context and explicitly labeled models; exact measured range accrual needs additional state.

## Optional stronger module: measured fee-growth history

This is a feasible extension, **not functionality supplied by the existing v4 package or verified in this research**. On an Ethereum endpoint serving **EXTENDED** blocks, index committed PoolManager storage changes. Derive the pool and boundary-tick slots from the pinned layout, retain their latest values, and compute fee-growth-inside using Uniswap's StateLibrary. For a real constant-liquidity segment, selected-token accrual is `floor(L × Δinside / 2^128)`, with uint256 modular subtraction and Uniswap-compatible rounding. A frozen FeeStrip series gives an especially clean segment. [StateLibrary](https://github.com/Uniswap/v4-core/blob/main/src/libraries/StateLibrary.sol)

This requires a complete state bootstrap/replay, source block hashes, ordinal ordering, deletion/reorg handling, and rejection of reverted calls; missing state must never silently become zero. Cached position `feeGrowthInsideLast` is not a current endpoint. Before the NFT's range existed, or across boundary clearing/reinitialization, an endpoint difference is not automatically a valid counterfactual backtest. Liquidity changes require segmenting actual position history. Do not present a current fixed-L extrapolation as its historical earnings. Firehose exposes storage-change address/key/old/new/ordinal and documents committed-call filtering; base blocks do not provide equivalent state data. [Ethereum data model](https://github.com/streamingfast/firehose-ethereum/blob/develop/proto/sf/ethereum/type/v2/type.proto), [base versus extended blocks and endpoints](https://docs.substreams.dev/reference-material/chain-support/chains-and-endpoints)

Add `Donate` extraction and label donations separately in the underwriting report. Fee growth includes donations; both donations and wash trading can make past income look attractive without indicating recurring demand. The entitlement must still follow FeeStrip's agreed fee-growth definition. [Uniswap PoolManager interface](https://github.com/Uniswap/v4-core/blob/main/src/interfaces/IPoolManager.sol)

For this stronger version, the live-provider spike must first demonstrate actual extended storage data for the chosen block range. The endpoint's existence alone does not prove its historical detail level. Cross-check sampled derived values against independent StateView/RPC reads and actual completed-series settlement; those checks validate the analytics but do not turn Graph data into a settlement witness.

## Exact developer path and access prerequisites

1. **Provider access:** obtain a free Graph Market account/API token and select the network/provider. The documented Ethereum endpoint is `mainnet.eth.streamingfast.io:443`; Sepolia is `sepolia.eth.streamingfast.io:443`. Export `SUBSTREAMS_API_TOKEN` only in the backend. Free monthly usage exists, but exact current allowances and sufficient backfill capacity must be checked in the dashboard; do not assume an unlimited historical replay. [Market authentication and plans](https://thegraph.com/docs/en/substreams/providers/the-graph-market/)
2. **Build/reuse:** install Substreams CLI and Rust/WASM toolchain; pin and build the module (`substreams build` from its directory). The source also gives `cargo build -p uniswap_v4_substreams --release --target wasm32-unknown-unknown`. Run `map_events` with `--network mainnet` against the authenticated provider, first on a bounded historical range, then following live blocks. Import its packaged output into FeeStrip's reusable analytics module. The upstream package can be consumed directly by a server or sunk to a local database; local storage is compatible with live provider input. [EVM developer path](https://docs.substreams.dev/tutorials/intro-to-tutorials/evm), [direct streaming](https://docs.substreams.dev/how-to-guides/sinks/stream)
3. **Database/runtime:** the published v4 walkthrough uses Docker, ClickHouse and optional Hasura. A Postgres sink is also documented. Use the package's cursor/reorg conventions, filter deleted rows, and avoid assuming a multi-event block's last loop iteration is its last execution. A hosted sink is optional, not an eligibility prerequisite. [v4 walkthrough](https://substreams.dev/showcases/uniswap-v4)
4. **Subgraph:** FeeStrip contracts must exist on a supported chain, with ABI and deployment block. Connect a wallet to Studio, create the subgraph, install Graph CLI/Node, implement schema/mappings, run `graph codegen` and `graph build`, then `graph auth <DEPLOY_KEY>` and `graph deploy <SLUG>`. Studio development indexing is free and rate-limited; the prize expressly accepts Studio provider data. Production publication is a separate onchain action with gas/indexing considerations; it is unnecessary merely to demonstrate live Studio data. [Subgraph quick start](https://thegraph.com/docs/en/subgraphs/quick-start/)
5. **Join and freshness:** pin the query deployment; include `_meta.block`, `_meta.deployment`, `hasIndexingErrors`, and the Substreams cursor/head/hash in diagnostic evidence. Join at a common observed block and disclose lag. Do not combine an ahead-of-head stream state with old series terms. [Graph metadata](https://thegraph.com/docs/en/subgraphs/querying/graphql-api/)

**Do not promise a turnkey Substreams-powered Subgraph deployment.** StreamingFast's v3 reference demonstrates `EntityChanges` → graph-node with a `kind: substreams` manifest. But the current v4 package outputs event protobufs for SQL; it is not that adapter. The official quick-start's SPS link currently lands on a 404, and inspected current Graph docs no longer contain SPS pages. This is documentation/support uncertainty, not proof that graph-node removed the capability. A new `graph_out` adapter plus confirmed Studio/indexer support would be additional work. The recommended application-layer composition avoids this dependency. [v3 reference](https://github.com/streamingfast/substreams-uniswap-v3), [v3 manifest](https://github.com/streamingfast/substreams-uniswap-v3/blob/develop/subgraph.yaml), [current Substreams quick start](https://thegraph.com/docs/en/substreams/quick-start/)

## Adoption evidence, demo proof and AI decision

Uniswap's own developer documentation links a live-network v4 Explorer deployment and supplies current/historical pool, swap and NFT queries. That is direct integration evidence. StreamingFast publishes runnable v4 source and a showcase. Neither proves FeeStrip buyer demand, current query freshness, audited data accuracy, or this new integration running. A source-listed deployment must be queried successfully and checked for lag before it can be represented as adoption proof in the demo. [Uniswap query guide](https://developers.uniswap.org/docs/ecosystem/subgraphs/guides/v4-query-examples), [linked Ethereum deployment](https://thegraph.com/explorer/subgraphs/DiYPVdygkfjDWhbxGSqAQxwBKmfKnkWQojqeM2rkLb3G?chain=arbitrum-one&view=Query)

The reviewable completion evidence should be: live provider heads advancing; the same reusable extractor used for two pool/series cases; one joined underwriting result that neither feed alone can produce; deterministic model methodology; and actual protocol payouts reconciling against displayed history. Save package pins, sample queries and reproducible run instructions in the public repo. A local fork/static JSON chart alone does not satisfy the prize's live-provider requirement.

**Do not add AI just to pursue another prize.** A useful later buyer analyst could answer “why is this claim cheaper?” by retrieving live terms/history, invoking deterministic break-even/replay tools, citing blocks, and producing a proposed quote requiring user approval. The Graph would be load-bearing, so the composable track plus the applicable AI pool could be a plausible submission strategy. The two AI pools (Start Fresh and Continuity) are alternatives based on project provenance; they are not two prizes to claim for the same build. The prize page does not establish guaranteed multi-track award stacking. Graph's MCP only supplies discovery/schema/query tools; it contains no model or valuation logic. [Subgraph MCP](https://thegraph.com/docs/en/subgraphs/tooling/subgraph-mcp/introduction/)

**Final recommendation:** pursue the composable track with the buyer-pricing integration as a core feature. Treat measured storage-derived fee history as a clearly scoped extension with a live-data verification gate. If the product would ship only a generic pool chart, choose the treasury-focused partner instead of stretching Graph or adding an ornamental AI agent.
