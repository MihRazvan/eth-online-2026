# Implementation workflow

Use the native capabilities of the actual IDE agent. These are operating principles, not a requirement to build an orchestration platform.

## Bootstrap once

Inspect current instructions, repository/remotes, branch rules, authenticated services, agent capabilities, runtime versions and browser access. Preserve teammate changes. Start a short status/acceptance ledger, a concise root instruction index and an AI-use record. Reuse adequate existing files. Commit a working baseline before branching concurrent writers.

Discover tools for the next concrete task, then begin implementation. Record unavailable RPC or deployment access as a specific gap. Tool installation, speculative framework comparison and document generation are not substitutes for working experiments.

## Ownership and parallelism

One lead owns integration, shared interfaces, root configuration and lockfiles. Use these responsibilities when there is useful independent work; they need not each become an agent:

| Responsibility | Boundary and output |
| --- | --- |
| Protocol/accounting | Contract state machine, asset movements, rights and contract-level tests |
| Historical proof | Genuine provider witness, authenticated root path, independent collection comparison, gas measurements |
| Aqua execution | Compatible runtime/encoder, program fixtures, actual claim/USDC trades |
| Graph data | Reusable EVM module, application subgraph, joined analysis and freshness/reorg semantics |
| Frontend | Rendered visual exploration, chosen design system and complete transaction flows |
| Independent reviewers | Economic properties and code review; separately, real browser/design critique |

Assign objective, base SHA, required context, owned/forbidden files, interface dependencies, acceptance evidence and return format. Use worktrees for concurrent writers; check their current directories. Isolate process ports, databases, RPC forks and transaction nonces. Worktrees alone do not isolate external state.

Prefer a few workers with substantial independent tasks. More agents are justified by independent work, not the desire to show a fleet. A blocked ABI consumer can work on fixtures against an agreed interface; it cannot silently redesign that interface. Do not let workers stage another worker's files.

Reviewers inspect actual code/app and return reproducible findings. Keep economically sensitive verification independent of implementation. If delegation is unavailable, perform explicit separate passes and report that honestly.

## Evidence-driven sequence

1. Establish reproducible baseline, interfaces and acceptance criteria. Explore visual directions in parallel with the highest-risk technical experiments.
2. Close genuine historical-proof and actual Aqua transfer risks; establish live Graph access. Document a blocker precisely if an integration cannot yet run.
3. Deliver one complete funded sale → trade → maturity → late capture → NFT return → independent redemption slice.
4. Expand market discovery, underwriting views, maker behavior and failure-state UX against that working slice.
5. Harden with stateful tests, independent review, browser critique, measured full gas costs and real integration evidence. Prepare deployment and sponsor documentation.

These are dependency gates, not time budgets or feature cuts. Continue other independent work when a credential or material product decision is blocked.

## Acceptance evidence

Each result records the commit, command, versions, scope (unit/fixture/fork/live), relevant chain/block/deployment, durable evidence path, result and remaining limitation. Distinguish `pending`, `running`, `passed`, `failed`, and `blocked`. A missing credential is never a passing live check.

Keep local and CI entry points aligned. Run relevant checks for each increment; broaden at integration boundaries or to resolve a specific risk. Preserve minimized regressions and important public witnesses. Keep bulky logs in suitable CI artifacts with durable summaries. Never commit secrets.

Required tests cannot be skipped, weakened or rewritten to fit a defect. Screenshot baseline updates require actual visual review. Legitimate expected-value changes require independent evidence and a recorded reason. Mutation runner exit status alone does not establish that mutations were caught.

## Checkpoint and recover

For each coherent increment: implement → verify → independent review where material → update status/evidence → inspect staged diff → commit → fetch/reconcile → push. Keep meaningful changes together. Avoid quotas, fabricated chronology and noisy one-line commits made only to resemble a human.

The user authorized commits and pushes to this project with existing authentication. Use configured identity, real timestamps and truthful attribution. One lead owns shared-branch pushes. Follow existing branch protection and checks; no force-push or overwriting teammate work. If remote/auth access blocks publication, retain local commits and continue useful work.

After restart or compaction, read the short status, current Git state and next task contract. Check relevant baseline health before resuming. Do not recreate the entire plan. Hooks may automate bounded formatting/checks or remind about status; they cannot grant permission or justify endless retries.

Record actual team decisions, reviews, coding and integration contributions. Give teammates concrete reviewable results without blocking every ordinary implementation choice. Do not invent their involvement. The submitted demo requires human narration under the supplied rules.
